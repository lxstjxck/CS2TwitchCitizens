# Technical findings — CS2 Twitch Citizens 0.3.0

## v0.7.0 OAuth findings

- Twitch's public Device Code Flow uses `POST /oauth2/device` with `client_id` and `scopes`, then `POST /oauth2/token` with the device code and device grant type. The public client does not need a client secret. Device responses supply `interval` and `expires_in`; the mod follows both. `GET /oauth2/validate` supplies the account user ID and login and confirms `user:read:chat`.
- Public-client refresh tokens are single use and can expire after 30 days of inactivity. The controller serializes refresh work, stores each rotated refresh token with DPAPI CurrentUser, and retries transient failures with a finite backoff. EventSub's subscription condition uses the validated user ID for both `broadcaster_user_id` and `user_id`.
- OAuth work runs outside ECS. `ViewerPanelUISystem` publishes only a sanitized auth view. The initial v0.7.0 attempt lacked access to the game's user environment and reported unavailable generator paths. A later audit verified `CSII_UNITYMODPROJECTPATH`, all Entities `1.3.10` generators, Burst `1.8.23`, ModPostProcessor, and the game assemblies. `Mod.props` reads several paths from the user environment, so `scripts/build-official.ps1` validates their process values and passes them as MSBuild properties. `ModPostProcessor.PathSet` additionally requires `CSII_UNITYVERSION` in the **user** environment; restoring it to the installed `2022.3.62f2` editor resolved its incomplete-toolchain error. Official Code Mod postprocessing, Burst for Windows/macOS/Linux, DeployWIP, and UI webpack installation passed. The deployed assemblies and UI banner were verified as v0.7.0. Runtime OAuth remains unverified.

### Query and relationships

`Game.Serialization.CitizenSystem.OnCreate` constructs a query with `ReadOnly<Game.Citizens.Citizen>()`, `ReadOnly<Game.Prefabs.PrefabRef>()`, and `Exclude<Game.Prefabs.RandomLocalization>()`. The read-only mod diagnostic uses `GetEntityQuery(ReadOnly<Citizen>(), Exclude<Game.Common.Deleted>())`. `Game.Common.Deleted` is a verified tag component. The diagnostic uses `CitizenUtils.IsDead(EntityManager, entity)` to skip dead Citizens and logs at most five living entities on the first `OnUpdate` and every 1,024 `OnUpdate` calls thereafter. It reads optional household, property, workplace and current building references only after component/existence checks. Its `home` field is a simple `PropertyRenter` path; tourists, homeless households, and other exceptional cases can legitimately log `Entity.Null`.

The core traversals verified from `Game.UI.InGame.CitizenUIUtils` are:

```text
Citizen entity --HouseholdMember.m_Household--> household
household --PropertyRenter.m_Property--> home property (when present)
Citizen entity --Worker.m_Workplace--> workplace/company
workplace --PropertyRenter.m_Property--> work property (when present)
Citizen entity --Student.m_School--> school
Citizen entity --CurrentTransport.m_CurrentTransport--> active transport/creature
creature --Resident.m_Citizen--> Citizen entity
```

`CurrentBuilding.m_CurrentBuilding` is a separate optional current-building reference. `Transform.m_Position` exists for world objects; a universal direct Citizen position lookup is **Not confirmed**.

## Naming

`Citizen` has no name field. `Game.UI.NameSystem.GetName(Entity,bool)` first checks `TryGetCustomName`; when a Citizen is selected it calls `GetCitizenName(Entity)`. `GetCitizenName` builds a localized `Assets.CITIZEN_NAME_FORMAT` from a first-name ID and a household-derived, gendered last-name ID. `Game.Common.RandomLocalizationIndex` is used by `NameSystem.GetId` and `GetGenderedLastNameId`. `NameSystem.SetCustomName(Entity,string)` exists and updates its dictionary plus the `CustomName` marker through `Game.EndFrameBarrier`. `NameSystem.Serialize/Deserialize` writes and reads the dictionary as `Entity`/string pairs. This confirms a game-supported custom-name path, but safe use by this mod and save/load behavior in a real city are untested; no Citizen is renamed by this project.

## Persistence

`Game.Citizens.Citizen.Serialize` writes state, health, birth day, pseudo-random value and other simulation fields; it writes no dedicated Citizen ID. `HouseholdMember.Serialize` writes its `Entity` reference via `Colossal.Serialization.Entities.IWriter.Write(Entity)`. The game's `Game.Serialization.SerializerSystem` uses `Colossal.Serialization.Entities.EntitySerializer` and `EntityDeserializer`.

Inspection of **Colossal.Core.dll** shows `BinaryWriter.Write(Entity)` looks up the entity in `m_EntityTable`, verifies its version, and writes the table index; `BinaryReader.Read(ref Entity)` resolves that index through its own `m_EntityTable` or returns `Entity.Null`. Thus the game's save format remaps entity references. Raw `Unity.Entities.Entity.Index`/`Version` is **not established as a stable cross-load key**. The working `NameSystem` serialization demonstrates that an Entity reference can be preserved *within the game's serialization context*, but this does not prove a standalone file containing raw Index/Version will resolve after reload.

No independent, globally unique persistent Citizen identifier was confirmed in the examined `Game.Citizens` types. Binding persistence remains unimplemented. A future approach may use the game's serializer to store a Citizen `Entity` reference in the same save context, subject to verification that a mod can register a serializable system/component and restore it safely. A save → exit → load test with actual game code is still required. The v0.2.0 registry uses `Entity` only as a temporary session key.

### v0.3.0 Twitch chat transport (7 October 2026)

- The transport is Twitch [EventSub WebSocket](https://dev.twitch.tv/docs/eventsub/handling-websocket-events), receiving [channel.chat.message v1](https://dev.twitch.tv/docs/eventsub/eventsub-subscription-types/#channelchatmessage) for one `broadcaster_user_id` and `user_id`. A WebSocket avoids a public webhook server. It connects to `wss://eventsub.wss.twitch.tv/ws`; after `session_welcome`, it creates the subscription with [POST `https://api.twitch.tv/helix/eventsub/subscriptions`](https://dev.twitch.tv/docs/api/reference/#create-eventsub-subscription), `transport.method=websocket`, and the received `session_id`. The WebSocket request uses a **user access token**, not an app token. The verified minimum scope for this path is `user:read:chat` granted by the account represented by `user_id`; `user:bot` and `channel:bot` are additional requirements for the app-token path, which this mod does not use.
- `clientId` is the registered Twitch application client ID. `accessToken` is a user access token with `user:read:chat`. `userId` is the ID of the account that granted the token and reads chat; the service checks it against Twitch's [token validation response](https://dev.twitch.tv/docs/authentication/validate-tokens) along with client ID and scope at startup and hourly. `broadcasterUserId` is the ID of the channel being watched; Twitch's [Get Users endpoint](https://dev.twitch.tv/docs/api/reference/#get-users) resolves a broadcaster login to that ID. Token acquisition is manual in v0.3.0; the official [Twitch CLI user-token command](https://dev.twitch.tv/docs/cli/token-command/) can obtain a testing token with `twitch token -u -s user:read:chat` after CLI setup. No client secret is used or stored by the mod.
- The service uses framework `ClientWebSocket`, `HttpClient`, and `DataContractJsonSerializer`, all compiled for `net48` and `net8.0`, with no Twitch or JSON NuGet package. The new `CS2TwitchCitizens.Twitch.dll` depends only on `CS2TwitchCitizens.Commands.dll` and framework libraries; it has no Unity/CS2 reference. Network code accepts `chatter_user_id`, `chatter_user_login`, `chatter_user_name`, and `message.text`; only `!join`/`!me` pass the existing parser and enter the existing concurrent queue. `CitizenBindingSystem` drains that queue and remains the only code touching ECS or bindings. Ordinary chat is not logged.
- Twitch [reconnect guidance](https://dev.twitch.tv/docs/eventsub/handling-websocket-events) distinguishes `session_reconnect` from a lost socket. On `session_reconnect`, the service opens the supplied `wss` URL on Twitch's EventSub host, waits for its Welcome, then disposes the old socket; Twitch transfers the subscription. On ordinary loss or keepalive timeout, it starts a new session and recreates the subscription after a bounded 2–64 second exponential delay. On disposal, cancellation and WebSocket abort stop network work without a synchronous game-thread wait. A bounded in-memory set suppresses repeated IDs of relevant EventSub command notifications, following Twitch's [at-least-once delivery rule](https://dev.twitch.tv/docs/eventsub/#handling-duplicate-events).
- Config example: repository `twitch.config.example.json`; runtime config: `%LOCALAPPDATA%\CS2TwitchCitizens\twitch.config.json` (`C:\Users\danil\AppData\Local\CS2TwitchCitizens\twitch.config.json` on this machine). Its fields are `enabled`, `clientId`, `accessToken`, `broadcasterUserId`, and `userId`; the real `twitch.config.json` is ignored by Git and lives outside the mod deployment directory, which official `DeployWIP` replaces. Missing, disabled, malformed, or incomplete config leaves the game systems running and starts no network service. When enabled, the automatic Debug DEV sequence is suppressed; when disabled, that sequence remains available. Tokens are never logged.
- Offline checks pass for ordinary chat rejection, parsed `!join`/`!me`, exact Twitch user ID and name fields, queue drain, malformed JSON, duplicate message IDs, safe reconnect URL interpretation, and bounded retry delays. Official compiler, Entities source generators, `ModPostProcessor`, Burst and `DeployWIP` passed with zero warnings/errors. Real Twitch authentication, WebSocket connection, subscription and notification delivery have **not** been tested with a user token.

## v0.4.0 API and implementation findings (8 October 2026)

- In the installed `Game.dll`, `Game.UI.NameSystem.TryGetCustomName(Entity, out string)`, `GetRenderedLabelName(Entity)`, and `SetCustomName(Entity, string)` are public. `SetCustomName` updates the NameSystem dictionary and queues a `Game.UI.CustomName` marker through `Game.EndFrameBarrier`. `NameSystem` implements the game's `ISerializable` and writes its custom-name dictionary as game-serialized Entity/string pairs. The v0.4.0 join path uses this API once after a successful binding. It records the previous custom name when present; otherwise it records the public rendered *label*, which is not proven to be the Citizen's full generated name. `NameSystem.Name` contains private fields, so the generated name's internal IDs are not accessed. The name may survive save/load while the mod's session binding does not; automatic name rollback is not implemented.
- `Game.UI.InGame.SelectedInfoUISystem.TryGetPosition(Entity, EntityManager, ref int, out Entity, out float3, out Colossal.Mathematics.Bounds3, out quaternion, bool)` is public static. Its internal target filter handles `CurrentTransport`, `CurrentBuilding`, and building targets for unspawned residents, and is used by the game's camera logic. The mod calls it on demand for a bound Citizen. It can return no position, which becomes `PositionUnavailable`; real positions in buildings and transport remain to be verified in a game run.
- `Game.UI.InGame.CameraUISystem.FocusEntity(Entity)` performs the game's focus operation but is private in this `Game.dll`. Its inspected implementation sets `Game.OrbitCameraController.followedEntity`, calls `TryMatchPosition` with `Game.Rendering.CameraUpdateSystem.activeCameraController`, then activates the orbit controller. ## v0.6.0 city-save serialization and life history (8 October 2026)

- The installed `Game.dll` has `Game.Serialization.SerializerSystem`, `SaveGameSystem`, and `LoadGameSystem`; there are no types named `SerializeSystem` or `DeserializeSystem` in this build. `SerializerSystem.OnUpdate` uses `Colossal.Serialization.Entities.EntitySerializer`/`EntityDeserializer`. `Colossal.Core.dll`'s `SystemSerializerLibrary.Initialize(World)` enumerates ECS systems implementing `IDefaultSerializable` and registers a `DefaultSystemSerializer<T>`. `Game.UI.NameSystem` is an existing example: its `Serialize<TWriter>` writes each `Entity` through `IWriter.Write(Entity)` and `Deserialize<TReader>` reads it through `IReader.Read(out Entity)`. The game's binary reader/writer use an entity table, so this is not raw `Index`/`Version` persistence.
- `CitizenBindingSystem` now implements `IDefaultSerializable`. Its format starts with integer version 1, then viewer and life counts. It writes Twitch user ID, login/display name, each LifeId, status, game dates, original name descriptor, last known age/home/workplace, optional cause, and the current active Citizen via the game writer. Completed lives write `Entity.Null` and retain their plain-value snapshots. No OAuth token or client secret is serialized. `SerializerSystem.SetDirty()` is requested if that system already exists when the binding system is created. The official postprocessor accepts this system.
- `Game.GameSystemBase.OnGamePreload` is subscribed to `GameManager.onGamePreload`; `OnGameLoaded` is subscribed to `LoadGameSystem.onOnSaveGameLoaded`. `LoadGameSystem.OnUpdate` runs the deserialize phase before invoking the loaded event. This allows the mod to clear prior city state at preload, read into a temporary list during `Deserialize`, then validate remapped Citizen Entities and rebuild the active registry after loading. Commands received during loading are discarded at restore completion because they have no reliable city context. The `OnGameLoadingComplete` hook handles a new game with no save section. `SetDefaults(Context)` handles older saves without mod data. `Colossal.Serialization.Entities.ObsoleteSystemSerializer.DeserializeSystem` skips unknown system blocks, supporting load without the mod installed; this path is confirmed from IL, not an in-game test.
- Unsupported format versions, invalid counts, duplicate viewer/LifeIds/Citizen claims, or other deserialization failures are logged and keep commands and mod save serialization blocked. Reading is transactional at the journal level; partially read data are never promoted to active bindings. After successful restoration, `!me`, `!find`, repeated `!join`, and the UI use rebuilt active bindings. The mod does not rename Citizens again on restore. A missing remapped Entity becomes `Missing` and cannot trigger automatic reassignment.
- `Game.Citizens.CitizenUtils.IsDead(EntityManager, Entity)` checks `Game.Citizens.HealthProblemFlags.Dead` (bit value 2). Every ten seconds the mod checks only bound Citizens. If the dead flag is present, it records the last age/home/workplace snapshot and `Game.Simulation.TimeSystem.GetCurrentDateTime()`, marks that life `Deceased`, and releases its claim. Home/workplace snapshots use `NameSystem.GetRenderedLabelName` when available and a presence placeholder otherwise; no raw Entity key is retained in completed history. If an Entity is unavailable for two checks, it becomes `Missing`, not `Deceased`; a missing position alone does not change life status. A later explicit `!join` creates a fresh GUID LifeId only after `Deceased`; `Missing` blocks replacement. Cause of death is left empty because no trustworthy cause was established.
- `!history` is parsed by the existing Twitch command path and logs only the sender's total/current/completed life counts and status. `ViewerPanelSnapshot` now includes current LifeId, total life count, status, and plain previous-life snapshots; JavaScript receives no ECS Entity. The current panel shows only count/status. Pure model tests exercise JSON roundtrip of the non-game DTO, transitions, duplicate protection, city isolation, and version rejection. The official binary writer/reader and actual save → exit → load cycle cannot be exercised offline; **runtime persistence is unconfirmed**.
